# 本地部署与设置接口安全边界

## 当前定位

V1 的 Localogue 是 **Local-First 单用户应用**。`/settings`、人物编辑、Evidence 生命周期、Canonical Commit 和 Restore 都属于具有文件系统写权限的管理功能。

当前版本尚未实现：

- 用户登录；
- 权限角色；
- CSRF / 多用户安全模型；
- 面向公网的管理面认证。

因此 V1 **不应直接暴露到不受信任的公网环境**。

## 为什么 `/settings` 能保存文件系统路径

Localogue 服务端需要读取本机或 NAS 上的资料目录。浏览器本身不能像桌面原生程序一样，把任意系统目录永久授权给服务器进程，所以当前方案是：

```text
浏览器输入路径
      ↓
PUT /api/settings
      ↓
服务端校验
      ↓
.localogue/settings.json
```

这对本机应用非常直接，但也意味着获得管理页面访问权的人能够改变服务端读取/写入的数据根目录。

## 部署建议

V1 推荐：

- 本机 `localhost`；
- 受信任家庭 LAN；
- Docker / NAS 时通过反向代理额外增加认证；
- 不将管理端口直接暴露到公网。

如果未来 Localogue 要成为可公开访问的服务器应用，应先设计完整的身份认证和权限层，再开放设置与写操作接口。

## 环境变量为什么仍保留最高优先级

服务器管理员可能希望容器启动参数决定数据目录，而不允许网页改变部署级挂载关系。因此：

```text
LOCALOGUE_LIBRARY_PATH 环境变量
        >
网页实例设置
```

网页仍可显示当前有效来源，但不能覆盖部署管理员显式设置的环境变量。
