# Community Data 共享原则

## 建议：共享，但与主程序仓库分离

Localogue 推荐把可合法共享的公共基础资料维护成独立 Community Data 仓库或 Shared Pack，而不是塞进主程序仓库。

主程序仓库负责：

- 代码；
- Schema；
- 受控词表；
- 文档；
- 完全虚构 Demo。

Community Data 负责：

- 人物稳定 ID；
- 日文正式名；
- 合理确认的别名、旧艺名、中文/英文映射；
- 出道/引退等事实字段；
- Work 番号、日期、时长、Maker/Label/Series 等事实型元数据；
- 来源与许可信息。

## “公开可见”不等于“可以重新发布”

数据共享要区分：

### 事实型字段

例如姓名、出生日期、番号、发行日期等事实通常比图片和文案更适合作为社区数据，但仍应保留来源并检查来源站点的使用条款与当地规则。

### 表达性内容

长篇简介、评论、编辑文案等可能具有明显表达性，不应默认整段复制后重新发布。

### 图片

头像、封面、剧照的版权风险最高。默认策略应是：

- 有明确许可才放进可分发 Asset Pack；
- 没有许可时保存来源 URL / Provider 关系，而不是直接重新打包；
- 支持用户在本地选择自己的头像和封面。

## 推荐仓库拆分

未来可以考虑：

```text
Localogue                  应用代码
Localogue-Community        结构化社区元数据
Localogue-Asset-Packs      可选、许可明确的图片资源包
```

具体仓库名以后再决定，架构上先保持分离。

## 来源追踪

Community Data 也应该逐步拥有自己的 Provenance：

```text
字段
来源站点 / 官方页面
采集或确认时间
贡献者
许可/备注
```

不能因为它是“社区资料”就失去可追溯性。

## 本地优先不是“禁止社区更新”

Community Data 提供大家可以复用的公共基础资料；Local Override 保存用户自己的修正和选择。读取时私人层优先，所以社区 Pack 更新不会强行覆盖用户本地版本。

V1-09 采用整实体覆盖。未来会把“事实修正”和“我喜欢哪张头像/封面”进一步拆开，其中后者属于 Presentation Preference，不应该要求用户复制或篡改社区事实实体。

社区资料长期共享还依赖稳定实体 ID，参见 [社区资料的稳定实体 ID](stable-community-ids.md)。
